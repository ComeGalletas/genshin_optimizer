## Phase 4: Conditions → ConstraintSpec

- [x] 4.1 `engine/constraints/spec.ts`: versioned zod schema (set requirements, mainStats, min/max stats, objective, exclusions, `keepEquippedOn`, teamBuffs, enemy)
  - [ADR-0036](adr/0036-constraint-spec.md). `packages/engine/src/constraints/spec.ts` (`zod/mini`): `version` 1, `character`, `weapon`, `buildLevel`, `defaults` (`extend`, the default, or `replace`), `set` (`4pc`/`2pc`/`2+2`/`any`), `mainStats` for sands/goblet/circlet (a stat or `any`), `minStats`, `maxStats`, `objective` (`crit_value`, `avg_damage`, a stat or `{ weights }`), `keepEquippedOn` (characters or `all`), `excludeArtifacts`, `teamBuffs`, `enemy` (`level`, `res`). Percent throughout, enemy resistance included; PLAN's `er >= 1.8` example now reads 180.
  - "Extend the defaults" comes from the Phase 3 acceptance: replacing them turned "Furina with ≥ 180% ER" into a search that timed out for the local model.
  - `parseConstraintSpec` checks the shape (strict at every level: an invented field like `pool` is an error) and then the meaning: keys exist, with the closest key suggested (`furnia` → `furina`, `GoldenTrope` → `GoldenTroupe`); the weapon suits the character; a 2+2 names two sets; each main stat can roll on its slot (listing the ones that can); no minimum above its maximum; `avg_damage` only with a damage profile; weights not all zero. It returns every issue at once, each with a path and a message written for a model, because zod/mini has no English messages. `sim` waits for Phase 5; account checks (owned character, artifact ids) belong to the mapping (4.2).
  - 14 tests (valid specs of every kind, strictness, each message, each meaning check, all issues at once). Loosening the schema or dropping the min/max check each turns them red.
- [x] 4.2 Spec → optimizer request mapping, with tests that each field changes optimizer behavior as intended
  - [ADR-0037](adr/0037-optimizer-spec-extensions.md). The optimizer gains what the spec needs: `maxStats` (leaf check, plus a prune once the running total passes a ceiling, admissible because pieces and set bonuses only add), a `weighted` objective (non-negative weights in the context; additive, so the scalar bound applies; `isObjective` still refuses it on web/API input), team buffs in the totals (not the base, which the damage formula scales by ATK%/HP%/DEF%; every bound starts from `sheetBase`), and the enemy (`level`, `res` in percent, converted once in `buildContext`).
  - `packages/engine/src/constraints/toRequest.ts` `specToRun(spec, account)`: the request, the context extras and the pool. Extends the curated defaults field by field (set and main-stat locks replaced or cleared with `any`, `minStats` merged with the spec winning, crit-ratio tiebreak kept); `replace` starts from nothing with crit value. From the account: the equipped weapon and build level, `keepEquippedOn` (the character's own pieces always stay) and `excludeArtifacts`; issues for a character with no weapon to use, an unknown artifact id, and a default floor above the spec's ceiling ("Bennett's default minimum er_pct is 180, above your maximum 150…").
  - Oracle tests (brute force vs branch-and-bound on random inventories): ceilings alone and with a floor and a 4pc; weights (2:1 crit weights pick exactly the crit-value builds); buffs (same pieces, crit value exactly +40 for +20 CRIT Rate; a floor reachable only through a buff); `avg_damage` with buffs and a ceiling (a 1000 flat ATK buff adds exactly 1000 effective ATK on the same pieces); enemy resistance −20% vs 10% scales damage by exactly 1.1/0.9 with the same ranking. Planting an over-eager ceiling prune, a bound that ignores buffs, or buffs folded into the base each turns them red.
  - 17 mapping tests on the sample account, through parse → map → `buildContext` → search, one per field showing it changes the result as intended (the Phase 3 question keeps 4pc Golden Troupe and the main-stat locks with ER ≥ 180). Planting "minStats replace instead of merge", "own pieces not kept under `all`" or "`any` set ignored" each turns them red.
