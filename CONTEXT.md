# CONTEXT — genshin-build-lab

Single-context project. This file is the canonical glossary; use these exact terms in code, issues, tests, and docs. Decisions live in `docs/adr/`.

## What this project is

A local Genshin Impact account advisor, forked from `natcat38/rpg-build-optimizer`. Given the artifacts a player owns, it finds the best 5-piece build for a character under chosen constraints and tells them what to farm to reach a meta target; the roadmap adds multi-source import with snapshot history, gcsim simulation and an LLM interface ([docs/PLAN.md](docs/PLAN.md)). The web app runs client-only, with no accounts, and shares builds as self-contained links; a local, single-user server owns everything else. See [ADR-0021](docs/adr/0021-local-first-server-architecture.md).

## Glossary

### Game domain

- **Artifact** — a gear piece. Occupies one **slot**, has one **main stat** and up to **4 sub-stats**.
- **Slot** — one of `flower`, `plume`, `sands`, `goblet`, `circlet`. A build is exactly one artifact per slot.
- **Main stat** — the artifact's primary stat. Flower/plume are fixed (HP/ATK); sands/goblet/circlet vary.
- **Sub-stat** — a secondary stat on an artifact (≤4, none equal to the main stat).
- **Artifact set** — a family of artifacts granting **set bonuses** at 2 and 4 pieces.
- **Set bonus** — the effect from wearing 2 (**2pc**) or 4 (**4pc**) of a set. The **flat-stat** portion of 2pc is scored from the frozen snapshot; 4pc effects are scored from a curated table (see below). Hit-kind-restricted **2pc** bonuses (Noblesse's Burst DMG, Golden Troupe's Skill DMG) are still unscored. See [ADR-0003](docs/adr/0003-stat-only-model-no-damage-engine.md).
- **Set bonus (4pc, full-uptime assumption)** — a 4-piece effect turned into a number by assuming it is always active at max stacks (Crimson Witch's 3 stacks ⇒ +22.5% Pyro DMG; Blizzard Strayer ⇒ +40% CRIT Rate against a Frozen target). Curated in `packages/engine/src/damage/setBonuses.ts`, each entry carrying its **uptime assumption** and source. A **sheet** bonus reduces to a flat stat and counts for every objective; a **hit-kind** bonus ("+35% Normal Attack DMG") counts only for `avg_damage`, weighted by that hit kind's share of the character's damage profile. Effects with no honest self-buff number — enemy RES shred, healing-scaled damage, reaction-only bonuses — are listed as deliberately **unmodelled** rather than scored as zero. See [ADR-0020](docs/adr/0020-four-piece-set-bonuses-at-full-uptime.md).
- **Passive (weapon or character)** — a weapon's refinement-scaled effect, or a character's talent passive, curated where it reduces to a sheet stat (`packages/engine/src/game/genshin/passives.ts`) and added to the build's base stats. **Static** passives (Aquila Favonia's +20% ATK at R1) count for every build. **ER-derived** ones (Engulfing Lightning's ATK, Mona's and Raiden's Elemental DMG) are resolved at the ER the build is optimised toward, like Emblem. A single known build's sheet (`sheetTotals`) resolves them at its own ER. Conditional parts (stacks, after a Skill) are left out and named in each entry's `notModelled`, and `passiveNotes` returns one line per passive saying what is counted. See [ADR-0042](docs/adr/0042-curated-weapon-and-character-passives.md).
- **Refinement** — a weapon copy's R1 to R5, from GOOD. A request's `refinement` is the owner's copy's: the one the character holds, else the most refined owned copy (`ownedRefinement`), else R1, which never overstates a passive.
- **2+2** — a build satisfying two different 2-piece set bonuses simultaneously. A 2+2 naming the same set twice is rejected at the share boundary as malformed; the optimiser defensively reads it as "≥2 of that set" so its bound stays admissible.
- **Stat keys** — `hp, hp_pct, atk, atk_pct, def, def_pct, em, er_pct, crit_rate, crit_dmg, elemental_dmg, physical_dmg, healing`. Percentage stats are stored in percent (crit rate `31.1`, not `0.311`), as GOOD stores them; flat stats (`hp`, `atk`, `def`, `em`) are plain numbers. See [ADR-0023](docs/adr/0023-engine-stats-in-percent.md).
- **Elemental DMG** — `elemental_dmg`; a **single fungible stat** combining all element-specific DMG% bonuses (Pyro/Hydro/…/Dendro). A goblet's element is tracked (`Artifact.element`) and an off-element goblet's main stat is zeroed before scoring. Physical DMG (`physical_dmg`) is separate. See [ADR-0011](docs/adr/0011-elemental-dmg-as-single-fungible-stat.md) and [ADR-0014](docs/adr/0014-element-aware-goblet-scoring.md).
- **Energy Recharge (ER)** — `er_pct`; commonly a minimum constraint (e.g. ≥160%). Every character starts from a **universal 100% base ER**; this game-wide baseline is supplied by the `genshinAdapter`, not the reference snapshot. See [ADR-0009](docs/adr/0009-adapter-owns-universal-game-baselines.md).
- **Elemental Mastery (EM)** — `em`.
- **Roll** — one increase to a sub-stat. Every roll, the first included, is one of four **roll tiers** (about 70/80/90/100% of the stat's maximum, equally likely), so the mean roll is 85% of the maximum. A 5★ artifact gets one roll per upgrade at +4, +8, +12, +16 and +20, on one of its 4 lines chosen uniformly. Tiers in `packages/engine/src/game/genshin/substatRolls.ts`.
- **Unactivated sub-stat** — the fourth line of a 3-line artifact, shown greyed out in game until the +4 upgrade activates it. Not part of the artifact's stats until then; Irminsul exports it as `unactivatedSubstats`.
- **Crit Value (CV)** — `crit_rate * 2 + crit_dmg`. A common **objective**.
- **Crit ratio** — the balance of crit rate to crit DMG (healthy ≈ 1:2). Used as a **soft tiebreak**, never a hard constraint.
- **Build level** — the single ascension-breakpoint level (default 90) at which **both** character and weapon are evaluated. See [ADR-0006](docs/adr/0006-inventory-import-and-build-level-model.md).

### Tool domain

- **Inventory** — the set of artifacts a player owns, loaded into the app.
- **Import** — populating the inventory: **GOOD file** (primary; full inventory) or **UID** (convenience; showcased characters only, via Enka.Network). See [ADR-0006](docs/adr/0006-inventory-import-and-build-level-model.md).
- **GOOD** — the community inventory-export JSON format produced by scanners. Every source is read through `normalizeGOOD` (`packages/engine/src/good/`): zod checks the structure, keys and locations are mapped to the dataset, and stat values pass through unchanged ([ADR-0023](docs/adr/0023-engine-stats-in-percent.md)).
- **GOOD issue** — one thing `normalizeGOOD` did not use as-is, with its path in the file: `invalid` (not valid GOOD), `unsupported` (valid GOOD this app can't score, such as a 3★ artifact), `unresolved` (a character or weapon key the dataset doesn't know, such as the Traveler) or `truncated` (a list longer than the importer reads). Nothing is skipped silently.
- **Fingerprint** — an artifact's identity across imports and sources: set, slot, rarity, level, main stat, element and the active sub-stats rounded to what the game shows (`packages/engine/src/import/fingerprint.ts`). Not unique: matching pairs pieces one to one, exact first, then a **fuzzy match** allowing one shown step per sub-stat (0.1, or 1 for flat stats) when exactly one candidate fits. See [ADR-0025](docs/adr/0025-artifact-fingerprint.md).
- **Sidecar** — the source-specific extras of an import (roll count, each line's first roll, astral mark, elixir crafted), kept beside the normalized inventory and keyed by **fingerprint** (`packages/engine/src/good/sidecar.ts`), so they survive import without entering the `Artifact` model the optimiser reads. Every value is checked against the game's rules before it is kept. A piece whose 4 first rolls are all known also gets a **first-roll key**, an identity that survives levelling.
- **Merge** — combining snapshots from several sources into one account view (`packages/engine/src/merge/`): values from the best-ranked source (Irminsul > OCR > other GOOD > Enka), location and lock from the newest snapshot, every appearance kept. See [ADR-0027](docs/adr/0027-merge-and-reconciliation.md).
- **Reconciliation report** — how two snapshots differ: pairs (exact, fuzzy, or **levelled** by first-roll key), **mismatches** (the only same-shape piece on each side, more than one shown step apart, not paired), **moves** (paired pieces whose location differs), and pieces only in one of them.
- **Scan fault** — a snapshot in which one fingerprint occurs 3 or more times, the mark of a scanner that kept re-reading one page. It is rejected, not merged ([ADR-0026](docs/adr/0026-irminsul-primary-ocr-fallback.md)).
- **Snapshot** — one imported file, stored in the local server's SQLite store (`packages/server/src/store/`) with its artifacts, roster, weapons and sidecar. Immutable, and identified by the file's SHA-256, so the same file imported again is the same snapshot. The **current account** is the latest recorded **merge** of snapshots. See [ADR-0028](docs/adr/0028-sqlite-snapshot-store.md).
- **Import diff** — what changed between two snapshots of the same account (`packages/engine/src/diff/`): new, gone, **upgraded** (paired by first rolls, or by **roll arithmetic**: every line's gain must be makeable from the upgrades' rolls, with one candidate only), moved, lock changes, and **unexplained** pairs it won't guess. See [ADR-0029](docs/adr/0029-import-diff.md).
- **Import center** — the web app's view of the local server's imports (`packages/web/src/import-center/`, Phase 8): the sources in precedence order, every snapshot with its import diff, each merge's **reconciliation report** (how each snapshot paired with the account merged before it: paired, mismatched, moved, only on one side), and the ways in (upload a GOOD file, scan the inbox). Shown only while the server runs. See [ADR-0049](docs/adr/0049-import-center.md).
- **Inbox** — `imports/inbox/` (git-ignored): drop a GOOD file there and `npm run inbox` (once, or `-- --watch`) imports it as a snapshot, using the file's time as when it was taken. Files stay in place; importing is idempotent. When a usable snapshot arrives, a new merge of the newest usable snapshot of each source kind becomes the current account; a faulty scan is stored but starts no merge.
- **LLM client** — the server's one way to call a language model (`packages/server/src/llm/client.ts`): a neutral `chat` shape (messages, tools, **tool calls**, a `stop` reason) translated to Ollama, an OpenAI-compatible server or Anthropic, whichever `config/llm.json` selects. The model is the interface, not the solver: it phrases what tools computed. **Explain** (`POST /explain`) is its first user: the engine's explain payload and prompt (`packages/engine/src/explain/`), one capped call. See [ADR-0033](docs/adr/0033-llm-provider-client.md).
- **Client-only** — the web app with no local server running: everything that works from the browser alone (GOOD import, optimizer, roster, teams, plan, share links). The app probes the server (`packages/web/src/local-server/`) on start and on tab focus; server-only features (explain, loading the server's account, later chat and simulation) appear only while it answers. See [ADR-0034](docs/adr/0034-web-and-local-server.md).
- **Grounding** — the chat's check that every number in an answer came from a tool result or the conversation (`packages/server/src/chat/grounding.ts`), as written or rounded to the answer's precision; integers up to 10 are exempt as counting words. A number written with a sign must match a source of the same sign, and a simulated comparison ("+7.4% ± 1.2%") must be exactly one a tool wrote (ADR-0047). A failing answer is sent back once, then its ungrounded numbers are **masked** as `[?]`. See [ADR-0035](docs/adr/0035-chat-tool-loop.md).
- **ConstraintSpec** — what the owner asked for, as data: the character, set rule, main stats, min and max stats, objective, pieces to leave alone (`keepEquippedOn`, `excludeArtifacts`), team buffs and enemy (`packages/engine/src/constraints/spec.ts`). A model writes it from a natural-language request; `parseConstraintSpec` checks its shape and meaning before anything runs. It **extends** the character's curated defaults unless `defaults` is `"replace"`. Percent units throughout. See [ADR-0036](docs/adr/0036-constraint-spec.md).
- **I understood** — the plain-words reading of a checked spec and its run (`describeRun`, `packages/engine/src/constraints/describe.ts`), each condition marked as asked or as the character's default, shown before anything runs and returned with every `optimize_build` result. The **translator** (`packages/server/src/llm/translate.ts`) gets there from words: the model submits a spec through one tool call, and every problem goes back to it for another try. See [ADR-0038](docs/adr/0038-spec-translator.md).
- **Golden set** — 31 natural-language requests (30 at first; the 31st exercises `objective: "sim"`, TODO 5.8) with the minimal spec each should become, on the committed sample account (`packages/server/src/llm/spec-golden.json`). `npm run spec:eval` scores a model on it: **equivalent** (the spec runs the same search as the expected one, the headline score) and **exact** (equal after canonicalising). Reports in `docs/spec-eval/`. See [ADR-0039](docs/adr/0039-translator-golden-set.md).
- **Rotation** — one team's gcsim action list in the rotation library (`rotations/<id>/`, ADR-0041): a template with a `{{slot}}` placeholder wherever a character acts, its **fight**, where it came from and how it was checked. `validated` when taken whole from a published config and reproducing its DPS within 2% on the pinned gcsim (or reviewed by the owner); `draft` when adapted or drafted and only run cleanly.
- **Slot (rotation)** — one place in a **rotation**'s team: the dataset keys that can fill it with the same actions, and its **role**. Not an artifact slot.
- **Fight** — what a **rotation** is simulated against: `actions` (the enemy has an hp too big to lose, so the run lasts exactly as long as the action list, as published community configs do) or `duration` (no hp, a fixed number of seconds). A team short of energy makes an `actions` fight longer instead of skipping actions.
- **Burst wait** — the time a **rotation**'s character spends waiting for their burst (energy or cooldown). gcsim stands idle by default, as published configs assume; `energyWait: "attack"` fills it with the slot's filler action (normal attacks unless set), which also puts the character on field to catch energy.
- **Rotation review** — what the owner reads before a drafted **rotation** counts (`npm run rotations -- review <id>`, ADR-0043): `review.md` with the result per character and one fight step by step (who is on field, their actions in KQM's notation, the team's damage and reactions), and the **fingerprint** of what was reviewed (template, reference builds, meta without status, validation and review). **Promotion** (`-- promote`) makes it `validated` only while the fingerprint still matches; no tool can do it.
- **Simulated re-ranking** — `objective: "sim"` in a **ConstraintSpec** (ADR-0044): the exact search's top K builds (default 20) by a stat objective, each simulated in a **rotation** with the owner's teammates as equipped (whose pieces are kept off-limits), ranked by mean team DPS with a 95% interval. A build whose difference to the best is inside that noise is a **tie**, and is reported as one.
- **gcsim support** — what the pinned gcsim implements, per character (`full`, `partial`, `unsupported`), weapon and artifact set: probed from the binary by `npm run sim:support` into `packages/engine/src/sim/gcsim-support.json`, stamped with the gcsim version (ADR-0045). Anything less than full makes a `"sim"` request **not simulated**: the stat search's builds, with `notSimulated` saying why.
- **Team comparison** — `simulate_team` (ADR-0046): a **base** team in a library **rotation** (each slot from the account as equipped) and up to five labelled **variants** (a swap within a slot, a weapon, a build, another rotation, another enemy), each run compared with the base as **vs base**: the difference in percent with its 95% interval, cited as "+7.4% ± 1.2%", and whether it is inside the noise.
- **Reference builds** — the build lines a **rotation** was checked on (`reference.gcsl`), from the published config(s) it came from; `npm run sim:check` runs every rotation on them.
- **Reference data** — the game "rulebook" (characters, weapons, sets, stat tables) from a frozen `genshin-db` snapshot. Never reads a player's account. See [ADR-0002](docs/adr/0002-frozen-bundled-reference-dataset.md).
- **Game version** — `gameVersion` in the reference snapshot: the newest game patch genshin-db records for any included character, weapon or set, derived at build time. Stored with `genshinDbVersion` and `generatedAt` (that release's date, not the build time). Shown in the header chip and footer.
- **Curation patch** — `CURATION_PATCH` (`packages/engine/src/curation.ts`): the patch the hand-curated tables (meta recipes, comp archetypes, damage profiles, 4pc bonuses, obtainability) were last verified against. The passive table records its own source version instead (genshin-db 5.2.14), and a test holds it to the installed genshin-db. Shown in the Teams note. It can lag the **game version**: newer characters are still optimised, without a meta target, damage profile or team slot.
- **Data coverage** — the report from `npm run data:coverage` (`packages/engine/src/data-coverage/`): per character and weapon, whether genshin-db has it and which curated tables cover it, plus gcsim support (unknown until Phase 5). Rows are the union of snapshot and curated keys, so a curated entry missing from genshin-db shows as a gap.
- **Levelling prospect** — an artifact below +20 ranked by its **expected** sub-stat score at +20 (remaining rolls at the mean roll, spread evenly over the 4 lines), against the +20 pieces of the same slot and main stat; on a tie the upgraded piece ranks first. Separate from the optimiser, which scores current stats only. `npm run prospects`; see [ADR-0024](docs/adr/0024-levelling-prospects-by-expected-value.md).
- **Constraint** — a hard requirement a build must satisfy (set requirement, minimum stats, per-slot main-stat lock). Infeasible constraints → `NO_FEASIBLE_BUILD`.
- **Main-stat lock** — a constraint fixing a slot's main stat (e.g. sands = `atk_pct`).
- **Objective** — what the optimiser maximises: a stat key, `crit_value`, or `avg_damage` (the v2 damage **target function**, available only for characters with a curated **damage profile**). Computed by `objectiveValue()`/`evaluateObjective()` in `packages/engine/src/optimizer/score.ts`. A `BuildResult.score` field is this objective value minus the crit-ratio soft-tiebreak penalty — it is **not** the same number as **Build score** below, despite the shared word; see "Five things called 'score'" at the end of this glossary. See [ADR-0016](docs/adr/0016-damage-engine-objective.md).
- **Optimiser** — the exact branch-and-bound search returning the **top-K** valid builds by objective score. Always exact, never approximate. See [ADR-0004](docs/adr/0004-exact-branch-and-bound-optimisation.md).
- **Diagnostics** — per-build data the optimiser emits: binding constraints, per-slot marginal contribution, explored/pruned counts.
- **Anti-clone cap** — the v1.0 results rule preventing near-identical builds from filling the top-K.
- **Build snapshot** — the self-contained state encoded in a **share link** (character, weapon, build level, five full artifacts, constraints, objective, meta target), and its team simulation when it was shared from one. A **shared comparison** (`#c=`) carries a whole team comparison, view only. See [ADR-0005](docs/adr/0005-self-contained-share-links.md) and [ADR-0051](docs/adr/0051-share-links-carry-simulations.md).
- **genshinAdapter** — the concrete object owning all game-specific data (characters, weapons, sets, base stats, main-stat values) and the universal game baselines. The optimiser, import, and share layers import it directly. (Originally a `GameAdapter` interface for multi-game extensibility, [ADR-0008](docs/adr/0008-gameadapter-seam-for-multi-game.md); collapsed to a concrete adapter — YAGNI, single game — in [ADR-0012](docs/adr/0012-collapse-gameadapter-seam-to-concrete-adapter.md).)

### v1.1 domain

- **Gap analysis** — the v1.1 centerpiece: compares the best **owned** build against a **meta target** and reports feasibility gaps, numeric shortfalls, and one grounded action. No random-roll simulation. See [ADR-0007](docs/adr/0007-gap-analysis-with-frozen-meta-snapshot.md).
- **Meta target / meta recipe** — recommended set(s), main stats per slot, ER target, crit-ratio target, endgame stat floors (`statTargets`), the guide's best-in-slot 5-star (`weapon`) and its best non-limited alternative (`weaponAccessible`), from a frozen KQM-sourced snapshot. Pre-fills the constraint builder; fully **overridable**. It is a build _recipe_, not a tier ranking.
- **Sample inventory** — the bundled, deterministic "Try a sample build" dataset (artifacts keyed `sample-…`) for instant, import-free demo (v1.1).
- **Sample preset** (a.k.a. **Sample build**) — one curated "Try a sample build" entry: a character plus a representative **constraint**, that loads the **sample inventory** and auto-runs the **optimiser**. Each preset demonstrates a different constraint mechanism (min stats, set requirement, main-stat lock).
- **Sample mode** — the app state where "Try a sample build" presets are offered: an empty inventory, or one containing only `sample-` artifacts. Importing real gear leaves sample mode, so a preset click can never overwrite owned artifacts.
- **Speed report** — the committed, reproducible benchmark (`docs/speed-report.md`, regenerated via `npm run bench`) showing how small a fraction of the brute-force build space the **optimiser** explores while still returning the exact optimum. See [ADR-0004](docs/adr/0004-exact-branch-and-bound-optimisation.md).

### v2 domain (endgame planner)

- **Damage profile** — a weighted set of stand-in hits approximating a character's rotation (multipliers transcribed at talent lv9). The input to the `avg_damage` objective.
- **Target function** — Σ weight × hit damage over a **damage profile**'s hits; the value the `avg_damage` **objective** maximises.
- **Enemy config** — the assumptions damage is computed against (enemy level and RES); default level 100 / 10% RES.
- **Build score** — a 0–100 composite of how built a roster character is (level, talents, weapon, artifact count, artifact quality), with explainable components. Computed by `computeBuildScore()` in `packages/engine/src/roster/buildScore.ts`. Distinct from the optimiser's **Objective**/`BuildResult.score` (a raw stat/crit/damage number, not 0–100) and from **Grade** below (a letter, not a number) — see "Five things called 'score'".
- **Grade** — a build's fit against a **meta target**, expressed as a letter (S/A/B/C/D): the mean of each `statTargets` entry's capped ratio (owned ÷ target). Computed by `gradeBuild()` in `packages/engine/src/meta/grade.ts`. Answers "how close to the meta recipe is this specific build", a narrower question than **Build score**'s "how invested is this character overall."
- **Comp archetype** — a curated 4-slot team recipe: one **role** per slot with ranked substitute characters.
- **Role** — a slot's function in a **comp archetype**: `on-field-dps | off-field-dps | buffer | sustain | battery | applicator`.
- **Team recommendation** — a **comp archetype** instantiated from the player's roster (real characters filling its slots).
- **Team score** — `tierWeight × mean(optionWeight × Build score)` for one instantiated **team recommendation**, computed by `teamScore()` in `packages/engine/src/teams/recommend.ts`. Ranks candidate team pairings against each other; treats **Build score** as an opaque input rather than recomputing it.
- **Endgame mode** — the endgame content a plan targets: `abyss | theater | stygian`. Spiral Abyss first.
- **Plan** — the composed output: **team recommendations** → per-member optimised builds → **farming list**. See [ADR-0019](docs/adr/0019-plan-output.md).
- **Allocation** — sharing one inventory out between N characters with no piece used twice (Phase 7). Each **allocation member** has a request (from their ConstraintSpec: set, main stats, floors, objective), the pieces their spec allows, a **priority** (lower picks first in the greedy pass) and a **weight** (their share of the plan's objective, for the improvement and exact passes; by default their role's: on-field DPS 2, off-field DPS 1.5, others 1). The **plan** is the eight-member Abyss case of it (`packages/engine/src/plan/allocate.ts`). The **plan's score** compares allocations: each member's build score over their **solo best** (their best build from everything their spec allows, as if alone), times their weight, averaged over the weights; 1 means everyone has their own best. **Allocation v1** improves the greedy pass by local search; **allocation v2** picks, exactly, the best plan within each member's top-M builds (ADR-0048). The **move list** turns a plan into what to do in the game: each planned piece not on its member, from whoever wears it at that point, following the game's swaps.
- **Farming list** — the deduped, name-prefixed feasibility and shortfall lines a **plan** aggregates from its members' gaps (`Plan.farming`). The UI calls it the "what to farm" list; never "shopping list".
- **Investment advice** — the ranked pull-and-craft recommendations derived from the near-miss **comp archetypes** the recommender reports (`packages/engine/src/invest/advise.ts`): which characters to pull for and which weapons to craft, ranked by the **Team score** points (specifically, its `bestPossibleScore` output) each would unlock. Acquisition advice, not levelling advice.
- **Teammates table (legacy, removed)** — `TEAMMATES` in `packages/engine/src/meta/teammates.ts` was a flat, unweighted per-character list of suggested partners with a one-line rationale, predating **comp archetypes**. It has been deleted (issue #90): `OptimizePanel`'s "Works well with" panel is now derived from `comps.ts` via `teammatesFor(characterKey)`, which picks the character's best-fit archetype slot and lists the ideal pick of every other slot as a teammate. `comps.ts` is now the single source of truth for "who teams with whom" — see [ADR-0017](docs/adr/0017-curated-comp-database.md)'s Status note.

### Five things called "score"

CONTEXT.md's own vocabulary and the code both use "score"/"grade" for five
different, non-interchangeable numbers. When writing an issue, test name, or
comment, name the specific one rather than the bare word "score":

| Term                                      | Function                                   | File                                       | Scale                                                | Answers                                                                           |
| ----------------------------------------- | ------------------------------------------ | ------------------------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------- |
| **Objective** value (`BuildResult.score`) | `objectiveValue()` / `evaluateObjective()` | `packages/engine/src/optimizer/score.ts`   | Stat-dependent (raw stat, crit value, or avg damage) | "How good is this specific 5-piece build, by the objective I chose?"              |
| **Build score**                           | `computeBuildScore()`                      | `packages/engine/src/roster/buildScore.ts` | 0–100                                                | "How invested is this roster character overall (level/talents/weapon/artifacts)?" |
| **Grade**                                 | `gradeBuild()`                             | `packages/engine/src/meta/grade.ts`        | Letter S–D                                           | "How close is this build to the meta target's stat floors?"                       |
| **Team score**                            | `teamScore()`                              | `packages/engine/src/teams/recommend.ts`   | Tier-weighted mean of Build scores                   | "How strong is this instantiated team, for ranking candidate pairings?"           |
| **Investment advice ranking**             | consumes `teamScore`'s `bestPossibleScore` | `packages/engine/src/invest/advise.ts`     | Same scale as Team score                             | "Which pull/craft unlocks the most Team-score points?"                            |

`objectiveValue` is the primitive of this hierarchy — `Build score` is a
separate, independently-defined composite (not built from `objectiveValue`),
while `Grade`, `Team score`, and the investment ranking each build on the one
before it. `packages/engine/src/roster/buildScore.ts`'s "Artifact quality" component calls
`objectiveValue(artifactContribution(a), 'crit_value')` directly per piece
rather than reimplementing the `crit_value` formula, so the two surfaces
cannot silently diverge (closed by issue #97; see the architecture audit,
`docs/research/audit-2026-09/architecture.md` finding #1).
